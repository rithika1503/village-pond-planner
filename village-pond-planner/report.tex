\begin{abstract}
Rural rainwater harvesting through village ponds is a low-cost,
high-impact water-conservation strategy, yet site selection remains
largely manual and expertise-dependent. This report presents the
\emph{Village Pond Planner}, a web-based geospatial decision-support
system that automates pond-site recommendation for any location in
India. Given a user-drawn polygon or a KML contour map, the system
fetches a 50$\times$50 Digital Elevation Model from the SRTM dataset
via Open-Elevation, applies the D8 flow-direction algorithm to
delineate the contributing catchment, queries nine years of ERA5
reanalysis rainfall from Open-Meteo, and estimates collectable water
volume using the Rational Method. A city-level search mode uses the
Photon geocoder to locate any Indian city or village and
automatically evaluates and ranks three candidate pond sites in
parallel. The system correctly identified catchment areas ranging from
29\,ha to 21{,}000\,ha in test cases across Pune, Hyderabad, and
Bhilai, with analysis latency of 3--8 seconds for the draw-polygon
mode and 10--20 seconds for the parallel top-3 city mode.
\end{abstract}

\keywords{Village Pond Planning, Geospatial Analysis, Rainwater
  Harvesting, Catchment Estimation, Web GIS, D8 Flow Routing, REST
  APIs, Open-Meteo, SRTM}

\section{Introduction}
\label{sec:intro}

India faces an acute rural water-access crisis: over 600 million
people experience high-to-extreme water stress, and traditional
village ponds (\textit{pokhar}, \textit{kunta}) that once supplied
communities year-round have fallen into disrepair or been encroached
upon. Government programs such as MGNREGA and PMKSY explicitly fund
new pond construction, but identifying \emph{which} piece of land
will accumulate the most runoff — and how large a pond should be —
requires terrain expertise that most village administrators lack.

This project builds a full-stack web application that replaces the
manual process with an automated geospatial pipeline. A user
interacts with a Leaflet map to either draw a polygon around
candidate land or upload a KML contour file exported from a local
survey. The backend analyses terrain, fetches historical rainfall,
estimates runoff, and overlays the recommended pond footprint,
catchment boundary, and key statistics on the map.

\subsection{Motivation}

Manual site selection is hard for three compounding reasons. First,
terrain complexity is invisible to the naked eye: a field that looks
flat may drain poorly, while a gentle depression 200\,m away may
collect runoff from a 500\,ha catchment. Second, historical rainfall
data are scattered across IMD district records that are not
programmatically accessible. Third, land ownership records
(Bhunaksha/DILRMP) are state-operated and often unavailable
digitally. An automated tool that works from open satellite DEMs
and public rainfall APIs eliminates the first two barriers and
provides a transparent proxy for the third.

\subsection{Scope of the Project}

The system supports the following:
\begin{itemize}
  \item Display satellite and street-map imagery for any location.
  \item Accept a user-drawn polygon or a KML/KMZ contour map as terrain input.
  \item Identify suitable land for pond excavation (slope, flow accumulation, OSM waterway exclusion).
  \item Delineate the catchment area contributing runoff via D8 flow routing.
  \item Query 9-year ERA5 historical rainfall from Open-Meteo.
  \item Estimate annual runoff volume (Rational Method: $V = P \times A \times C$).
  \item Recommend pond depth and approximate storage capacity.
  \item Overlay all results on the interactive map.
  \item Auto-recommend top-3 pond sites for a named city/village.
\end{itemize}

The system does \emph{not} perform structural or civil engineering
design of pond embankments, conduct legal land-ownership verification,
or support real-time hydrology monitoring.

The system is a three-tier web application:

\begin{enumerate}
  \item \textbf{Frontend (Browser)} — Plain HTML/CSS/JavaScript with
    Leaflet.js for mapping and Leaflet.draw for polygon input. No
    build step required; served by Python's \texttt{http.server}.
  \item \textbf{Backend (FastAPI / Python 3.14)} — A single
    Uvicorn-hosted ASGI application with four routers:
    \texttt{analysis} (draw-polygon), \texttt{city} (top-3
    recommendation), \texttt{contour} (KML upload), and
    \texttt{health}. All handlers are \texttt{async}; CPU-bound
    NumPy work is offloaded to a thread pool via
    \texttt{asyncio.run\_in\_executor}.
  \item \textbf{External APIs} — Open-Elevation (SRTM DEM),
    Open-Meteo (ERA5 rainfall), OSM Overpass (waterways), and
    Photon/Nominatim (geocoding). All calls use \texttt{aiohttp}
    with per-request session creation and 12-second timeouts.
\end{enumerate}

\subsection{Technology Stack}

\begin{itemize}
  \item \textbf{Backend:} Python 3.14, FastAPI 0.115, Uvicorn, aiohttp, NumPy, SciPy, Matplotlib, Shapely.
  \item \textbf{Frontend:} Vanilla HTML5/CSS3/ES2020 JavaScript, Leaflet 1.9.4, Leaflet.draw 1.0.4.
  \item \textbf{Elevation API:} Open-Elevation (SRTM 30\,m resolution).
  \item \textbf{Rainfall API:} Open-Meteo ERA5 reanalysis (\texttt{total\_precipitation\_sum}, 9 years, ~27\,km resolution).
  \item \textbf{Geocoding:} Nominatim → Photon fallback chain.
  \item \textbf{Waterway data:} OSM Overpass API.
  \item \textbf{Containerization:} Docker + docker-compose (production deployment).
\end{itemize}

\section{Methodology}
\label{sec:methodology}

\subsection{Terrain and Elevation Analysis}

The bounding box of the user's polygon (or city bbox) is used to
construct a regular 50$\times$50 lat/lon grid. This grid is POSTed to
the Open-Elevation API in a single batch request, returning SRTM
elevation in metres for each point. The result is stored as a NumPy
2-D array $E[i,j]$.

For KML input, contour lines are parsed from the \texttt{<LineString>}
elements; each line's elevation is read from the \texttt{<name>}
tag. Scipy's \texttt{griddata} (Delaunay linear interpolation)
then interpolates the sparse contour points onto the same 50$\times$50
grid.

Slope is estimated from finite differences of $E$ in both axes
and converted to degrees:
\[
  \theta = \arctan\!\left(\sqrt{\left(\frac{\partial E}{\partial x}\right)^2
    + \left(\frac{\partial E}{\partial y}\right)^2}\right)
\]

\subsection{Catchment Area Delineation}

Flow direction is computed cell-by-cell using the D8 (deterministic
eight-direction) algorithm: each cell drains to whichever of its
eight neighbours has the steepest downhill gradient. Flow
accumulation $A[i,j]$ is then the total number of upstream cells
draining through $(i,j)$.

Candidate pond locations are cells where:
\begin{itemize}
  \item Slope $< 8°$ (gentle enough to excavate),
  \item Accumulation is above the median but below the $p_{98}$
    stream-channel threshold (collects water without being an active
    river), and
  \item Not within 2 grid cells of an OSM-mapped waterway.
\end{itemize}

The best candidate's outlet cell is snapped to the highest-accumulation
neighbour within a search radius. Catchment area is traced by following
D8 pointers uphill from the outlet, summing contributing cell areas
using the Haversine formula to account for latitude-dependent
cell size.

\subsection{Rainfall Data Integration}

Open-Meteo's ERA5 endpoint is queried with the centroid of the
analysis area:
\begin{verbatim}
GET https://archive-api.open-meteo.com/v1/archive
  ?latitude=<lat>&longitude=<lon>
  &start_date=<YYYY-01-01>&end_date=<YYYY-12-31>
  &daily=precipitation_sum&timezone=auto
\end{verbatim}
Nine complete years (current year $-$ 10 through current year $-$ 2)
are requested, summed to annual totals, and averaged to produce
$\bar{P}$ in mm/yr. The source and number of years are reported
alongside the estimate so evaluators can verify reproducibility.

No authentication is implemented (course prototype). Third-party API
failures are handled with try/except around every \texttt{aiohttp}
call; if Open-Elevation returns a non-200 response, the system logs a
warning and falls back to a synthetic flat DEM. If Open-Meteo fails,
a \texttt{500} is returned with a descriptive message. The geocoder
uses a two-provider fallback chain: Nominatim → Photon, so a single
blocked provider does not break city search.

\subsection{Frontend and Visualization}

The interface is a \emph{wizard}: only one step is visible at a time,
revealed progressively as the user completes each stage.

\textbf{Area path:}
\begin{enumerate}
  \item Method picker → choose ``Select Area on Map''.
  \item City search (optional, zooms map to city).
  \item Mode: ``Top 3 Sites'' or ``Analyze My Area''.
  \item For Top 3: click \emph{Find Best Sites} → three ranked cards
    appear with numbered markers and catchment overlays on the map.
  \item For Draw: draw land polygon → optional catchment polygon →
    Analyze → results panel + map overlays.
\end{enumerate}

\textbf{KML path:}
\begin{enumerate}
  \item Method picker → ``Upload Contour Map''.
  \item Upload KML/KMZ file, select parameters, click Analyze.
  \item DEM and flow-accumulation PNG images are returned (base64)
    and displayed inline beneath the form.
  \item Result panel shows catchment, volumes, pond dimensions.
\end{enumerate}

\subsection{Database and Storage}

The system is intentionally stateless: no database writes occur
during a request. All computed results are returned directly in the
HTTP response as JSON. This choice eliminates an entire failure
domain (DB connection pooling, schema migrations) for a course
prototype, and all inputs required to reproduce a result are
parameters of the original request. A production version would write
recommended sites to a PostGIS database for longitudinal tracking
and comparison.

The two most significant CSD themes in this project are
\textbf{concurrency} and \textbf{resilience}. Concurrency was
critical because the city recommendation endpoint must call
Open-Elevation, OSM Overpass, Open-Meteo, and run D8 routing for
three candidate sites — all within a reasonable user wait time. Using
\texttt{asyncio.gather} reduced the top-3 latency from ~30\,s
(serial) to ~12\,s (parallel). Resilience was equally critical
because all three external APIs (Open-Elevation, Nominatim, Open-Meteo)
are rate-limited public services with occasional outages. Every
external call is wrapped in a try/except with a sensible fallback,
ensuring the application remains functional even when individual
services are unavailable.

\section{Discussion and Limitations}
\label{sec:discussion}

\textbf{What worked well:} The D8 pipeline is fast and accurate for
moderate-relief terrain. Open-Meteo's ERA5 API is reliable,
well-documented, and returns 9+ years of data in one request.
The fallback geocoder chain means city search works even when
Nominatim is rate-limited.

\textbf{Limitations:}
\begin{itemize}
  \item \textbf{DEM resolution:} Open-Elevation serves SRTM at
    30\,m native resolution, but our 50$\times$50 grid over a city
    bbox corresponds to ~250\,m per cell. This means small depressions
    $<$250\,m across are invisible to the algorithm.
  \item \textbf{Flat terrain:} D8 flow routing on very flat surfaces
    (Thar Desert, Deccan Plateau) produces unrealistically large
    catchments. A production system would apply the Priority-Flood
    DEM conditioning step.
  \item \textbf{Land ownership:} Classification is terrain-heuristic
    (flow accumulation ratio as a proxy for government drainage land).
    Actual Bhunaksha shapefile integration is needed for legal accuracy.
  \item \textbf{OSM waterway quality:} OSM river data in rural India
    is incomplete. Unmapped rivers will not be excluded from the
    candidate set, potentially suggesting sites inside active channels.
\end{itemize}

All AI-generated code was reviewed line-by-line, understood, and in
several cases substantially modified before being committed. The D8
flow-accumulation implementation was rewritten after the AI-generated
version failed on non-square grids (fixed by using explicit row/column
indexing rather than flat index arithmetic). The land-status
classification was changed from a random-weighted draw (AI suggestion)
to a fully deterministic terrain-based rule set after evaluation
revealed non-reproducible results.
